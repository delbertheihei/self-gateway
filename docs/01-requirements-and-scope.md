# SGW 需求与范围说明书

> 项目：**SGW / Self Gateway**（本地 AI 用量观测网关）
> 角色：产品需求文档（PRD）
> 版本：v1.0 · 设计冻结
> 关联文档：[`00-agent-dev-spec.md`](./00-agent-dev-spec.md) · [`02-architecture-design.md`](./02-architecture-design.md)

---

## 1. 背景与痛点

### 1.1 现状
- 本机通过 **Codex（Desktop/CLI）** 使用 AI 编码能力。
- 鉴权方式是 **API Key**，由公司统一通过 **sub2api 中继**分发：

```toml
# C:\Users\<user>\.codex\config.toml （现状，已脱敏）
model_provider = "OpenAI"
model = "gpt-6-luna"

[model_providers.OpenAI]
name = "OpenAI"
base_url = "https://relay.example.com/v1"        # 公司/自建的中继地址（因环境而异）
wire_api = "responses"                          # ← 走 OpenAI Responses API
requires_openai_auth = true
experimental_bearer_token = "sk-****"           # ← 分发到个人的 Key
```

### 1.2 痛点
| # | 痛点 | 影响 |
|---|---|---|
| P1 | **没有 sub2api 账号**，看不到自己的配额与消耗 | 不知道今天/本周用了多少，无法自我节流 |
| P2 | 中继侧统计是**黑盒**且**不可自证** | 无法核对账单，无法判断是"我用的"还是"被摊派的" |
| P3 | 无法回答"**哪个任务/哪个会话最烧 token**" | 无法优化 prompt 习惯，也无法向主管解释用量来源 |
| P4 | 出问题时无法自证 | 请求失败/降级/被限流时，缺少本地一手证据 |

### 1.3 机会
把 Codex 的出口指向**本机一个只读旁路网关**，请求原样转发，网关在旁路把"谁在什么时候用了多少 token"记成一本**本地账本**。技术上零侵入、零改造上游、零依赖公司配合。

## 2. 目标与非目标

### 2.1 目标（v1 必须达成）
| ID | 目标 | 可衡量指标 |
|---|---|---|
| **G1** | 请求 100% 原样穿透 | 请求体/响应体 SHA-256 与直连一致（见 `00-agent-dev-spec.md` H1/H3） |
| **G2** | 本地可见精确用量 | 上游带 `usage` 时，账本与响应逐字段相等；覆盖率 ≥ 95% |
| **G3** | 明细日志可开关 | 关闭时零明细落盘；开启时可回看任意一次请求的元数据 |
| **G4** | 现代化仪表盘 | 首屏 < 1s 出 KPI；支持按时间/模型/会话下钻 |
| **G5** | 轻量 | 单进程、单端口、冷启动 < 1s、空载常驻内存 < 120MB、空闲 CPU ≈ 0% |
| **G6** | 可随时回滚 | 一条命令切回直连，Step 数 ≤ 1 |

### 2.2 非目标（v1 明确不做）
- 不做协议转换、prompt 改写、内容审核、结果缓存、语义去重
- 不做限流/配额熔断/多 Key 轮询/故障转移（v1 只**观测**不**管控**）
- 不做多用户、登录体系、云端同步、团队看板
- 不做移动端；不做成本"权威"结论（价格可配，仅供参考）

### 2.3 后续版本候选（v2+，本文只登记不设计）
V2-1 预算告警（阈值 + 系统通知） · V2-2 prompt 模板级归因 · V2-3 多 Provider 聚合 · V2-4 导出 CSV/Parquet · V2-5 与 sub2api 返回的配额头对账

## 3. 用户与场景

### 3.1 唯一用户画像
**"我"** = 一名在本机使用 Codex 的开发者，拥有多个并行项目（如 `c4plus/micro-service`、`tts-api`），一天内会开多个 Codex 会话，关心"今天花了多少 / 哪个会话最贵 / 这个月会不会超"。

### 3.2 核心用户故事

| ID | 故事 | 验收要点 |
|---|---|---|
| US-01 | 作为我，我想让 Codex 走网关而**感觉不到差别** | 不改 Codex 使用方式；流式输出、工具调用、推理过程**无可见变化** |
| US-02 | 作为我，我想在首页一眼看到今日/本周的 token 与请求数 | 打开 `http://127.0.0.1:8787`，KPI 卡在 1s 内出数 |
| US-03 | 作为我，我想看到用量随时间的趋势 | 面积图：token 按小时/天，可切 input/output/cached/reasoning 分项 |
| US-04 | 作为我，我想知道哪个模型/哪个会话最烧 token | 模型排行榜 + 会话下钻列表，支持按 token 排序 |
| US-05 | 作为我，我想排查"刚才那次为什么慢/为什么失败" | 请求表可按状态码、错误类型、慢请求筛选，点开有耗时瀑布 |
| US-06 | 作为我，我想**控制**是否记录请求明细 | 一个开关；关闭后不再新增明细，且能一键清理历史明细 |
| US-07 | 作为我，我想（可选）看到每次请求的 prompt/响应正文 | 第二个开关，默认关闭；开启有醒目隐私提示；可定时清理 |
| US-08 | 作为我，我想随时关掉网关回到直连 | `scripts` 一条命令 + 设置页有"复制回滚配置"按钮 |
| US-09 | 作为我，我想确认网关没在偷改我的请求 | 设置页/详情页有"透传自检"入口，一键跑 H1~H5 回归 |

## 4. 功能需求（FR）

### 4.1 FR-A 透明转发（P0，核心）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-A1 | 监听 `127.0.0.1:8787`（仅回环，禁止 `0.0.0.0`），对外提供 `/v1/*` | P0 |
| FR-A2 | 请求体**流式**转发，字节级不变（H1） | P0 |
| FR-A3 | 请求头零白名单透传，仅剥离逐跳头（H2） | P0 |
| FR-A4 | 响应头与响应体字节级不变（H3） | P0 |
| FR-A5 | 路径/查询原样拼接，仅替换 base 前缀（H4） | P0 |
| FR-A6 | 默认不注入/不改写 `Authorization`；提供**显式**上游密钥替换开关（默认关，H5） | P0 |
| FR-A7 | 支持 SSE 流式透传：不做整包缓冲、首字节即刷、不做压缩解压-再压缩 | P0 |
| FR-A8 | 客户端中断 → **先宽限期排空上游**（默认 8s，为拿到终止事件的 usage），随后 abort 上游 | P0 |
| FR-A9 | 上游超时/错误分类映射（见 `00` §7），4xx/5xx 原样透传不重试 | P0 |
| FR-A10 | 上游 TLS 支持自定义 CA（`caFile` / 允许不安全开关，默认关闭校验放松） | P1 |
| FR-A11 | 支持 `responses`（Codex 唯一使用的协议）与 `models` 的观测；`chat/completions` 仅作原样转发（Codex ≥ v0.95 已移除该协议，不投入观测适配） | P1 |
| FR-A13 | **上游 usage 完整性自检**：启动/首轮检测 `response.completed.response.usage` 是否含 `input_tokens`/`output_tokens`/`total_tokens`；缺失即告警（该结构会让 Codex 整轮失败） | P0 |
| FR-A12 | 上游 `/v1` 前缀的**黄金用例探测**与自动兼容（避免 `/v1/v1`） | P0 |

### 4.2 FR-B 用量采集（P0）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-B1 | 从非流式响应体提取 `usage`（含 `*_tokens_details`） | P0 |
| FR-B2 | 从 SSE 中提取 `response.completed` → `response.usage` | P0 |
| FR-B3 | 从 chat 流式尾部 usage chunk 提取（若上游返回） | P1 |
| FR-B4 | 无 usage 时启用本地估算（tokenizer / 启发式），并标记 `source='estimated'` | P0 |
| FR-B5 | 记录计时：总耗时、上游连接耗时、上游首字节（TTFB）、首 token 延迟、token 速率 | P0 |
| FR-B6 | 记录状态码、错误分类、请求/响应字节数、`x-request-id`、`response.id` | P0 |
| FR-B6b | 记录 Codex 身份头：`session-id`、`thread-id`、`x-client-request-id`、`originator`、`x-openai-subagent`（原样，仅用于本地归因） | P1 |
| FR-B7 | 会话归组：优先用 Codex 请求头中的会话标识，缺失则用响应 id 回填 | P1 |
| FR-B8 | Key 指纹：`sha256(Authorization)` 前 8 位，用于区分不同 Key（不存明文） | P1 |
| FR-B9 | 可配置价格表（每 1M token，区分 input/output/cached），据此估算成本 | P1 |
| FR-B10 | 观测**绝不影响**主链路（H6）：旁路溢出即丢弃观测 | P0 |

### 4.3 FR-C 明细日志开关（P0）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-C1 | **Detail Mode**：总开关，关闭时仅落聚合、不落逐请求明细 | P0 |
| FR-C2 | **Body Mode**：子开关，落盘 prompt/响应正文（默认关，受 Detail Mode 约束） | P0 |
| FR-C3 | 开关变更立即生效（≤1s），不需重启 | P0 |
| FR-C4 | 开关状态持久化（存 DB，重启保留） | P0 |
| FR-C5 | 落盘正文单条大小上限（默认 512KB）+ 超限截断标记 | P1 |
| FR-C6 | 保留策略：明细按天/容量滚动清理（默认 30 天；正文默认 7 天；上限 2GB） | P0 |
| FR-C7 | 一键清理：清空明细 / 清空正文 / 清空全部（二次确认） | P1 |
| FR-C8 | 打开 Body Mode 时 UI 必须显示醒目隐私提示（正文可能含代码与密钥） | P0 |

### 4.4 FR-D 仪表盘与查询（P0）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-D1 | **概览页**：KPI（今日/本周 token、请求数、估算成本、失败率、p95 延迟、缓存命中率） | P0 |
| FR-D2 | **趋势图**：堆叠面积图（input/output/cached/reasoning），粒度 小时/天，范围 24h/7d/30d/自定义 | P0 |
| FR-D3 | **模型分布**：按模型 token 占比（环形或条形）+ 表格 | P0 |
| FR-D4 | **请求表**：时间、端点、模型、状态、耗时、token、来源（精确/估算）；分页 + 排序 + 筛选 | P0 |
| FR-D5 | **详情抽屉**：耗时瀑布（排队/建连/TTFB/首token/生成）、token 明细、错误信息、正文（若开启） | P0 |
| FR-D6 | **会话视图**：按会话聚合的 token 排行与下钻 | P1 |
| FR-D7 | **实时**：新请求实时出现在表头（<1s），KPI 增量刷新 | P1 |
| FR-D8 | **设置页**：开关、保留策略、价格表、上游地址、透传自检、回滚指引 | P0 |
| FR-D9 | 数据导出：请求明细 CSV、聚合 JSON | P2 |

### 4.5 FR-E 运维（P1）

| 编号 | 需求 |
|---|---|
| FR-E1 | 一键切换脚本 `point-codex.ts`：备份 `config.toml` → 改 `base_url` → 输出回滚命令 |
| FR-E2 | 启动自检：端口占用、DB 可写、上游连通性、CA 校验，结果写入日志与设置页 |
| FR-E3 | 结构化日志（pino），敏感字段自动脱敏 |
| FR-E4 | 健康检查 `GET /_sgw/api/health`，含版本、uptime、DB 大小、开关状态 |
| FR-E5 | 开机自启可选（Windows 计划任务 / `pm2` / NSSM），文档给出步骤不给实现 |

## 5. 非功能需求（NFR）

| 维度 | 指标 | 说明 |
|---|---|---|
| **性能** | 首字节延迟增量 p95 < 5ms；吞吐 ≥ 200 req/s（本地压测） | H7 |
| **资源** | 空载 RSS < 120MB；50 并发流式 RSS < 350MB；空闲 CPU ≈ 0% | 轻量化要求 |
| **可靠性** | 网关崩溃不得影响 Codex 重试；重启后账本不丢（WAL + 批量提交） | 数据以"尽力而为 + 幂等"为准 |
| **可维护性** | 模块边界强约束；**运行时依赖 ≤ 3 个**（`zod` / `pino` / `eventsource-parser`），零原生模块 | 见 `03` |
| **可观测性** | 自身也有日志与指标；能回答"网关自己有没有拖慢我" | FR-D5 的瀑布图 |
| **安全** | 仅监听回环；校验 `Host`/`Origin` 防 DNS rebinding；不存明文密钥；正文默认不落盘 | H8/H9 |
| **隐私** | 无外发遥测；`keyFingerprint` 单向；导出前提示含敏感内容 | H8/H9 |
| **可移植** | Windows 11 优先，macOS/Linux 应可运行（不依赖 Windows API） | 便于以后复用 |
| **可测试** | 透传回归可脚本化；SSE 可用假上游（mock SSE server）离线测试 | 见 `06` |

## 6. 约束与假设

| 类型 | 内容 | 影响 |
|---|---|---|
| 约束 C1 | 技术栈锁定 **Node.js + TypeScript** | 选型已在 `03` 落地 |
| 约束 C2 | 上游 sub2api 是**黑盒**，不可改、不可依赖其统计接口 | 只能被动观测响应 |
| 约束 C3 | 上游 `wire_api = "responses"` | 观测器必须支持 Responses SSE 事件族 |
| 约束 C4 | 本地无 Docker / 无外部数据库 | 必须嵌入式存储 |
| 假设 A1 | Codex 对 `127.0.0.1` 的 `http://` base_url 可正常工作 | 若否则启用 mkcert 自签 HTTPS 方案（`02` §9） |
| 假设 A2 | 上游会在响应中返回 `usage`（绝大多数中继会原样透传） | 若不返回则退化为估算（FR-B4） |
| 假设 A3 | Codex 会在请求头携带某种会话标识 | 若否则用响应 id 兜底归组 |
| 假设 A4 | 单机单用户，QPS 峰值 < 10 | 允许"无锁写 + 批量提交"的简单并发模型 |
| 风险 R1 | 上游可能对 `Origin`/`User-Agent` 等做校验 | 透传策略天然规避（H2） |

### 关键待验证项（实现第一步用探针回答，均为源码调研后仍无法确定的部分）
1. 上游是否返回 `usage`？在流式与非流式两种情况下分别如何？
2. ⚠️ **若返回 `usage`，`input_tokens`/`output_tokens`/`total_tokens` 三个字段是否齐全且为整数？**
   （Codex 的 `ResponseCompleted` 把这几个字段声明为非 `Option`：**缺 `total_tokens` 会让 Codex 整轮硬失败**。这是本项目的最高优先级探针项）
3. `response.completed` 中 `response.id` 是否存在（同属硬失败字段）。
4. SSE 事件族与事件名实际形态（是否为标准 Responses 事件；是否出现 `codex.*` 私有扩展）。
5. 响应是否使用 `Content-Encoding` 压缩；是否回显或替换 `x-request-id`；是否回显 `x-codex-turn-state`。
6. Codex 实际请求的头集合（`originator` 取值、`session-id`/`thread-id`/`x-client-request-id` 是否都在）。
7. `base_url` 拼接语义：上游是 `{base}/responses` 还是 `{base}/v1/responses`（`GET /v1/models?client_version=` 是否可用）。
8. Codex Desktop 的实际版本是否开启 `supports_websockets`（若开启则会改走 `ws://`，本网关不支持）。

## 7. 成功标准（v1 发布判据）

| 判据 | 阈值 |
|---|---|
| 透传硬约束回归 | H1~H5 全绿（`00` §9.1） |
| 用量覆盖率 | usage 精确命中率 ≥ 95% 的请求 |
| 计数准确率 | 精确命中场景 100% 逐字段一致（`00` §9.3） |
| 延迟代价 | TTFB p95 增量 < 5ms |
| 日常使用无感 | 连续使用 3 天，未出现一次因网关导致的 Codex 异常 |
| 开关有效 | 关开关后 `data/` 无新增明细，一键清理后磁盘占用下降 |
